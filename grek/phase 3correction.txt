- The page list/grid must scroll underneath/below it.

- Do not duplicate the toolbar for every page.

2. PAGE THUMBNAIL GRID
==================================================

Target:

.editor-thumbnails__grid

This is the actual page thumbnail container.

The pages MUST be genuinely draggable and reorderable.

Requirements:

- Click/touch and drag a page thumbnail.
- Move it to another position.
- Show a clear insertion indicator.
- Drop it between pages.
- Support moving to the first position.

==================================================
3. AUTO-SCROLL WHILE DRAGGING
==================================================

When dragging a page inside:

.editor-thumbnails__grid

the thumbnail container must automatically scroll when the pointer/finger approaches the top or bottom edge.

Example:

User drags page 2 downward.

They reach the bottom of the visible thumbnail area.

The container should automatically scroll downward so additional pages become reachable while the user continues dragging.

Likewise:

- Near top edge → scroll upward.
- Near bottom edge → scroll downward.

The user must be able to drag a page from the beginning of a large document to the end without manually stopping, scrolling, and restarting the drag.

Requirements:

- Smooth auto-scroll.
- Appropriate scroll speed based on distance from the edge.
- Do not scroll when the pointer is safely inside the central area.
- Stop scrolling when the pointer leaves the edge zone.
- Do not accidentally scroll the main PDF workspace instead of the thumbnail container.
- Support mouse and touch as far as the browser/platform permits.

Test with documents containing at least 20–50 pages.

Requirements:

- Dragging top-left changes width and height from that corner.
- Dragging top-right works independently.

- Dragging bottom-right works independently.
- The opposite corner acts as the appropriate anchor.
- The element must not jump when resizing begins.
- The element must not randomly change position.
- Width/height must remain valid.
- Resizing must work at all zoom levels.
- Resizing must work after rotation.
- Resizing must work for different page sizes.
- Resizing must work on touch devices where supported.

Do not substitute side handles for the requested corner handles.

Do not consider the feature complete until all four corners have been tested.

Currently, actions such as:

- Dropping
- Resizing
- Rotating
- Reordering
- Editing

appear to cause the page/document to reload or remount.

Fix this.

Normal editing operations MUST NOT reload the browser page.

They must also avoid unnecessarily remounting the entire PDF workspace.

Investigate the actual cause instead of masking the symptoms.

Check for:

- Accidental form submissions
- Buttons behaving as submit buttons
- State changes causing full application remounts
- Unstable React keys
- Document/session state being recreated
- File/blob URLs being regenerated unnecessarily
- PDF document instances being destroyed/recreated
- Effects with incorrect dependencies
- Router/navigation calls
- Parent components unnecessarily remounting the editor
- Persistence logic triggering document reloads
- Drag/drop handlers recreating the entire document state

Editing one element should update only the necessary state/rendering.

7. DRAGGING
==================================================

Dragging an element must feel continuous.

While dragging:

- The element follows the pointer.
- No page reload occurs.
- No visible document reset occurs.
- The selection remains active.
- The element does not disappear/reappear.
- The viewport does not unexpectedly jump.
- The PDF renderer does not unnecessarily restart.

When the user releases the pointer:

- Commit one final position.
- Create one logical undo/redo entry.
- Persist the change through the existing persistence system.

Do not persist/reconstruct the entire document on every pointer movement.

==================================================

- Create one logical history entry.

==================================================
11. FIT TO PAGE — CORRECT THE MEANING
==================================================

Audit the existing "Fit to Page" implementation.

Fit to Page means:

THE ENTIRE PDF PAGE should fit inside the available viewing area.

It should calculate the appropriate scale using:

- Available viewport width
- Available viewport height
- PDF page width
- PDF page height
- Current workspace/sidebar dimensions

For a portrait page, the complete portrait page should be visible.

For a landscape page, the complete landscape page should be visible.

For different page sizes, calculate the scale dynamically.

Do not simply set a generic zoom percentage.

Do not confuse Fit to Page with Fit to Width.

Fit to Width:

- Page width fills the available horizontal viewing area.
- Vertical scrolling may remain necessary.

Fit to Page:

- Entire page fits within the available viewing area.
- No part of the page should be clipped.

Both modes must actually behave differently.
